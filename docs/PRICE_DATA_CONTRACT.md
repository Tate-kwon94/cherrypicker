# 가격 데이터 계약

체리피커의 기본 추천에 사용하는 가격은 아래 필드를 모두 가져야 합니다.
사용자 직접 등록 가격은 현재 비교 세션에서만 사용하는 보조 데이터이며 기본
추천 데이터와 합쳐 저장하지 않습니다. 사용자가 별도 저장한 비교 결과만 기기
브라우저의 `내 비교함`에 남습니다.

## 상품 식별

- `productId`: 내부 상품 ID
- `brand`, `name`
- `barcode` 또는 판매처 상품 코드
- `unit`: `ml`, `g`, `개`
- `volume`: 실제 비교에 사용하는 용량 또는 수량

상품명만으로 같은 상품이라고 판단하지 않습니다.

`variantId`는 아직 없습니다. 대신 **검수 대상을 본품으로 한정**해 변형이
갈릴 여지를 없앴습니다 — 아래 "검수 대상은 본품뿐입니다"를 보세요.
`variantId`를 도입하기 전에 이 문단을 먼저 고쳐야 합니다.

## 가격 관측값

- `retailerId`, `sourceUrl`
- `channel`: `duty` 또는 `retail`
- `listPrice`, `shipping`, `instantDiscount`
- `finalPrice`
- `currency`
- `inStock`
- `observedAt`, `expiresAt`
- `collectionMethod`: 승인 API, 제휴 피드, 운영자 검수

특정 카드, 개인 쿠폰, 회원 등급처럼 모든 사용자가 받을 수 없는 할인은
`finalPrice`에 섞지 않고 조건부 가격으로 분리합니다.

## 판매 조건

- 출국장 수령 여부
- 출국일 또는 터미널 제한
- 회원 등급
- 결제수단
- 최소 구매금액
- 픽업 매장
- 수령 방식: 공항 수령, 국내 배송, 주류매장 픽업, 편의점 픽업
- 지점별 재고와 확인 시각
- 성인 인증 필요 여부

## 추천 포함 기준

다음 중 하나라도 충족하지 못하면 기본 추천에서 제외합니다.

1. 상품 변형이 명확하게 매칭되어야 합니다.
2. 원본 URL과 확인 시각이 있어야 합니다.
3. 최종 가격 계산 요소가 모두 숫자로 검증되어야 합니다.
4. `expiresAt`을 지났거나 최신성 기준을 벗어난 값은 추천에서 제외합니다.
5. 오래된 값은 최근 30일 안에서만 `참고가격`으로 표시할 수 있습니다.
6. 가격 수집 방식이 승인된 운영 정책 안에 있어야 합니다.

## 확정된 결정

아래는 코드만 봐서는 "아직 안 한 것"과 구분되지 않는 항목들입니다. 의도적으로
닫아 둔 것이므로, 여는 데는 각 항목이 적은 선행 조건이 필요합니다.

### USD 가격 등록은 닫아 둡니다

`price_offers`에 `currency` 컬럼은 있고 비교 계약도 통화가 다른 쌍을
거부하지만, **등록은 KRW만 받습니다**. 금액 컬럼이 정수라 `$89.50`을 담을 수
없고, 89로 절사해 저장하면 통화를 바로잡으려던 변경이 더 조용한 오류를
만듭니다.

여는 조건: 금액을 최소 단위(센트·원)로 저장하는 마이그레이션. 그때까지 컬럼과
계약 검사는 **다른 경로로 들어온 USD 행을 거부하기 위해** 살려 둡니다.

### 사용자가 캡처한 가격은 저장하지 않습니다

`내 입력 포함 비교`에는 저장 버튼이 없고, 캡처한 가격은 새로고침하면
사라집니다. 근거는 두 가지입니다.

- 캡처는 그 시점 화면의 사본입니다. 다시 검증할 방법이 없으므로 시간이
  지나면 맞는지 틀린지 아무도 모르는 금액이 됩니다.
- 손으로 입력한 가격을 기기에 남기는 것은 프라이버시 표면을 늘리는데,
  Phase 0에서 그 대가로 얻는 제품 가치가 없습니다.

`SavedPickBasis`에 `"captured"` 멤버가 없는 것이 이 결정의 구현입니다 —
검사로 막는 게 아니라 표현할 수 없습니다. 여는 조건: 캡처 가격의 보존 기간과
재검증 방법을 정하고, 저장 사실을 사용자에게 알리는 방식을 확정하는 것.

### 저장된 선택은 상품을 가리킵니다

`내 비교함` 항목의 식별자는 `${category}:${productId}`이고, 주류도
**병의 카탈로그 id**를 씁니다. 취향 키(`beginner`)를 쓰면 그 취향의 추천 병을
바꾸는 순간 저장된 항목 전부가 사용자가 고른 적 없는 상품을 가리킵니다.

### 검수 대상은 본품뿐입니다

기획세트, 선물세트, 증정품 포함 구성, 한정판, 묶음 수량(`2개입`, `1+1`)은
검수 가격으로 **등록하지 않습니다**. 등록 검증이 상품명을 보고 거부합니다.

이 제품에는 아직 변형(`variantId`) 개념이 없어서 상품 id가 곧 변형입니다.
그 상태에서 세트와 본품이 같은 id로 들어오면 구성이 다른 가격이 같은 상품으로
비교되고 — 기획세트가 본품보다 싸 보이는 식으로 — 비교 계약의
`variant-mismatch` 검사는 두 값이 같으므로 막아주지 못합니다.

검수 대상을 본품으로 한정하면 그 모호함이 사라집니다. 이름으로 거르는 것은
추측이지만, 통과시키면 잘못된 비교가 **조용히** 만들어지는 반면 잘못 걸린
경우에는 사람이 보고 판단할 수 있습니다.

여는 조건: `products`에 `variantId`를 도입하고 파일럿 카탈로그를 본품·세트·
에디션 기준으로 다시 적는 것.

### OCR 언어 데이터는 CDN에서 받습니다

Tesseract worker와 wasm 코어는 자체 호스팅으로 옮겼습니다 — 그 둘이 제3자
출처가 **우리 페이지 안에서 코드를 실행하는** 통로였고, `script-src`에서
제거했습니다.

언어 데이터(`kor.traineddata`)만 계속 jsdelivr에서 받습니다. 코드가 아니라
데이터이고, 최악의 경우가 OCR이 가격을 잘못 읽는 것인데 그 값은 사용자 확인을
거치며 공개 결론에는 절대 쓰이지 않습니다. `connect-src`에 사실대로 적어
두므로, 나중에 옮기면 OCR이 조용히 실패하지 않고 CSP 위반으로 드러납니다.

## 권장 저장 구조

실제 데이터 소스가 확정되면 D1에 다음 구조를 추가합니다.

- `products`
- `product_variants`
- `retailers`
- `price_observations`
- `offer_conditions`
- `product_matches`

현재 `.openai/hosting.json`은 `DB` 논리 바인딩을 사용합니다. 운영자가
등록한 가격은 `draft` 상태로 시작하고, 검수 후 `approved`가 되어야 공개
대상이 됩니다.

## 최신성 정책

증거 종류별로 추천에 사용할 수 있는 기간이 다릅니다.

| 증거 | 최신 기간 |
| --- | --- |
| 판매처 공식 페이지 | 1일 |
| 성인 인증 주류 픽업 | 7일 |
| 영수증·매장 가격표 | 3일 |

이 표의 **정본은 `app/lib/freshness.ts`** 이며, 등록 검증·공개 피드 판정·
사용자 문구가 모두 그 한 곳을 읽습니다. 문서와 코드가 어긋나면 코드가
맞습니다. 기간이 지난 값은 삭제하지 않고 최근 30일 안에서 `참고가격`으로
내려 표시하며 체리픽 계산에서는 제외합니다.

30일 조회 보존과 90일 등록 유효기간 상한은 최신성과 **다른 기준**입니다.
전자는 참고가격을 언제까지 보여줄지, 후자는 만료 시각이 확인 시각보다
터무니없이 뒤인 입력을 막는 검사입니다. 세 값을 하나로 합치지 않습니다.
